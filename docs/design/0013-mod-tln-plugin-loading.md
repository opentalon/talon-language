# ADR 0013 — `mod.tln`: loading plugins from the core CLI

Status: proposed · closes the "add a plugin with no Go" gap ([#19](https://github.com/opentalon/tln-language/issues/19))

## Context

The connector runtime (ADR 0012) lets a program name a plugin — `connector
"inventory" via mcp { … }` — and the CLI already routes `tool "inventory" …`
through a registered plugin factory. But **nothing registers the factory** in the
`tln` CLI: today only a Go host (`WithPlugin` / `WithToolResolver`) can. So
`tln run rules.tln` with a connector errors, and "add the mcp plugin" means
writing a Go program.

The obvious fix — compile tln-mcp into the `tln` CLI — is not allowed: tln-mcp
imports tln-language, so core importing it back is a **module dependency cycle**,
and it violates the invariant that core has zero dependency on any plugin.

## Decision

Adopt the **Bundler model** (Ruby's `Gemfile` + `bundle install`). A project
declares its plugins in **`mod.tln`**; **`tln bundle`** materializes them; then
**`tln run`** uses them — with **no hand-written Go** and **core importing no
plugin**.

### `mod.tln` — the manifest (the `Gemfile`)

One line per plugin, exactly like `gem "rails", "7.0"`:

```tln
plugin "mcp" "v0.4.0"                                    # → github.com/opentalon/tln-mcp
plugin "io"  "v0.1.0"                                    # → github.com/opentalon/io-tln
plugin "db"  "v0.9.0" store                              # a FactStore plugin
plugin "acme" "v1.2.0" from "github.com/acme/tln-acme"   # third-party source
```

- `plugin "<name>" "<version>"` — `<name>` is the identifier a program uses in
  `connector "…" via <name>`. The source module defaults by convention to
  `github.com/opentalon/tln-<name>`, overridable with `from "<module>"`.
- `store` marks a FactStore plugin (default is a tool plugin).
- **Core ships no plugins.** Even `io` is its own plugin ([io-tln](https://github.com/opentalon/io-tln)), declared like any other — no built-ins, no special cases. You bundle exactly what you use, like Bundler with no implicit gems.

### `tln bundle` — the `bundle install`

Ruby `require`s a gem at run time. Go cannot load Go code at run time without the
cycle/dlopen mess, so instead of *loading* we **generate and compile**:

`tln bundle` writes a small, project-local bootstrap module (`.tln/bundle/`) that
imports core + each declared plugin module and registers its factory —

```go
// GENERATED by `tln bundle` — the user never writes or sees this
tln.WithPlugin("mcp", tlnmcp.Factory)
tln.WithPlugin("db",  tlnstore.Factory)
```

— then runs `go build` to produce a project-local `tln` binary with those
plugins baked in, pinned by `mod.lock`. **No cycle:** the generated module is a
leaf that depends on core *and* the plugins; core still depends on neither.

### `tln run`

`tln run rules.tln` uses the bundled binary (re-execs `.tln/bundle/tln` when a
bundle exists), which has the factories registered, so a `connector "…" via mcp`
block resolves and runs. `env` values come from the process environment
(`WithEnv(os.Getenv)`). The connector routing (ADR 0012) does the rest.

### End to end — zero Go

```tln
# mod.tln
plugin "mcp" "v0.4.0"
plugin "io"  "v0.1.0"
```
```tln
# rules.tln
connector "inventory" via mcp { endpoint env "INV_URL" bearer env "INV_TOKEN" }
workflow "w" {
  step "list" { tool "inventory" "list-items" { query "x" } }
  step "log"  { tool "io" "writeln" { text "done" } }
}
```
```bash
tln bundle          # like `bundle install` — fetch + compile the plugin set
tln run rules.tln   # connectors resolve; no main.go, ever
```

## Why not a separate bundled CLI (`tlnx`)

A hand-written second binary that imports core + plugins works but is a parallel
CLI to maintain. The Bundler model gives the same in-process speed while keeping
`tln` the only command — the bundle is *generated* from `mod.tln`, not
hand-authored. Rejected.

## Alternative considered: out-of-process plugins

Launch each plugin as a subprocess over a stdio protocol (Terraform-provider
style). Pro: language-agnostic plugins, no Go toolchain at install. Con: every
plugin must ship a server binary + speak the protocol, and per-call IPC. Kept as
a future option for non-Go / third-party plugins; the Bundler model is the
default because tln's own plugins are Go and in-process is simpler and faster.

## Consequences

- `tln run rules.tln` works from a `connector` block with no Go. "Add a plugin" =
  a line in `mod.tln` + `tln bundle`.
- Core stays plugin-free; the generated bundle carries the plugin deps.
- Requires a Go toolchain for `tln bundle` (as Ruby needs a compiler for native
  gems). A future stage can ship prebuilt bundles to drop that.
- This is both halves of #19 — plugin system *and* package manager — in one
  mechanism.

## CLI surface

```
tln init <name>     # scaffold a project: <name>/mod.tln + <name>/rules.tln + .gitignore
tln bundle          # resolve mod.tln → generate bootstrap → go build → write mod.lock
tln run <file.tln>  # re-exec the bundled binary (has the plugins) to run the program
```

`tln init` writes a ready-to-edit skeleton so a newcomer goes from zero to a
running connector program in three commands (`tln init x && cd x && tln bundle`).

## Stages

1. Plugin factories: **io-tln** and **tln-mcp** export `Factory` matching
   `tln.PluginFactory` (io-tln reads `path`/`stream`; tln-mcp reads
   `endpoint`/`bearer`), each tagged/released — the bundle compiles these, so
   they must be published first.
2. `mod.tln` grammar + parser + `mod.lock` (manifest + resolution) in core.
3. `tln init <name>` — scaffold `mod.tln` + `rules.tln`.
4. `tln bundle` — generate the bootstrap module, `go build` the project-local
   binary, write `mod.lock`.
5. `tln run` — re-exec the bundle when present (plain `tln run` otherwise).

## Update — store plugins (Active Record)

A **store** plugin (a `FactStore`, e.g. tln-db) is not a per-call connector — a
run has exactly one backing store — so it is selected by config, not wiring:

- `mod.tln`: `plugin "db" "v0.1.0" store` declares it (bundled via its module).
- `config/store.tln`: `store db { target env "TLNDB_ADDR" }` gives the
  connection (env-resolved at run time; absent file → in-memory default).
- The plugin exposes `Factory(ConnectorSpec) (FactStore, error)`; `tln bundle`
  emits `tln.LoadStoreConfig("config/store.tln")` → `Factory` → `WithFactStore`.
- Precedence: host `WithFactStore` > the manifest store plugin + config >
  in-memory. At most one store plugin.

This keeps the store selection convention-driven (Active Record): the same
program runs on memory, tln-db, or a future datalevin plugin depending only on
`mod.tln` + `config/store.tln`. A sidecar store (tln-db) still runs its server
separately; the bundle carries only the client.
